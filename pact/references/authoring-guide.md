# PACT 写作精度指南 —— 每节「写到什么程度算够」

> 创建日期: 2026-07-26
>
> 判定一节是否达标，用同一把尺子：
> **一个一无所知的实现者读完这节，还需要问问题吗？还需要自己做决定吗？**
> 需要 → 没写够。

## 通用反例（任何一节出现即不达标）

| 反例 | 为什么不行 | 改成 |
|---|---|---|
| 「按需处理」「视情况而定」「后续再定」 | 把决策推给实现者 | 现在定，或回访谈门问 |
| 「返回用户信息」 | 哪些字段？什么类型？ | 给 schema 或表格 |
| 「性能要好」 | 不可判定 | 「列表 P95 < 300ms」 |
| 「参考现有实现」 | 冷读者没有"现有实现" | 摘录关键结论进正文 |
| 「详见 xx 文档」 | 破坏自足性 | 摘录 + 附出处 |
| 「合理地处理错误」 | 无法验收 | 列错误情形表 |

## P 层

### P1 一句话定义与交付形态
**够**：读者能立刻回答「这是个什么东西、给谁、跑在哪」。
**不够**：只写产品名和愿景。
> 反例：「本项目是一个智能化的管理平台。」
> 正例：「面向中小企业财务专员的报销审批系统。交付形态：PC 管理后台（Vue 3 SPA）
> + 移动端小程序。部署在客户内网，由运维用 nginx 托管静态产物。」

### P2 背景与问题
**够**：读者能自己推断出「遇到没写到的取舍时该往哪边倒」。
**不够**：只写「为了提升效率」。要写清现状怎么做的、痛在哪、不做的代价。

### P3 用户与角色
**够**：每个角色的**数据可见范围**和**可执行写操作**都明确。
**不够**：只列角色名。角色表不写权限范围，`C8` 就没有基调。

### P4 核心场景

**本节是给人看的主视图来源**——`pact-book.html` 的「业务流水线」整块由它生成。
人审规格不是按 P/A/C/T 的分类轴读，是**顺着业务跑一遍**；写不好这一节，人就只能去啃全文，然后点头了事。

**够**：
- **节点是人真能打开的页面或真在跑的功能点**，判据：**能指着说「它在这儿」**。
  指不着的（「订单服务」「校验模块」）是架构，写 `A2`，不写这里。
- **回头路必须画**（取消 / 驳回 / 退回 / 超时）——退回类分支是最常被漏掉的流程。
- 每个节点下用**人话**写清单，一句一条，句尾反引号挂 R-ID。四个组名固定：
  `能做什么` / `什么情况会被拦住` / `谁看得到什么` / `背后自动发生了什么`。
- **样本数据必须来自用户**。编出来的金额、时长、科室名看起来像真的，人会当真，
  **反向污染他对系统的理解——比没有样本更糟**。样本本身就是第一批该问人的东西。

**不够**：
- 只写 happy path。异常分支是需求，不是实现细节——它们进「什么情况会被拦住」。
- 句子写成字段罗列（「输入：3 件；输出：订单号」）。**人靠读句子、反驳句子来审需求**，
  字段表激发不出反驳，一段像话的描述才行。结构化精度不会丢，它在 `C` 层。
- 写了没有 R-ID 的行为。没 R-ID = 这条需求不存在，回 `P5` 立条目或删掉这句。

**两个必须标出来的东西**：
- **AI 替用户做的决定**：那半句用 `**加粗**`，并在该句下缩进一行写 `- ⚠ 我定的：<为什么是我定的>`。
  这些是人审阅时**唯一必须逐条裁定**的东西——其余要么是他自己说过的，要么是他判断不了的推导。
- **规格接不上的地方**：句首写 `⛔` 并说明缺什么（缺接口 / 缺状态迁移 / 缺文案），
  **不许顺手编圆**。走不通只有真走一遍才知道，静态 lint 查不出来。

> **一条主流程超过 12 个节点** = 这不是一条流程，是两条，拆开。
> 写法与标识约定（`/路由`、`$ 命令`、`POST /api/x`、`@无界面功能点`）见 `templates/PACT.md` 的 P4 段，
> 完整实例见 `references/example-PACT.md`。

### P5 需求清单
**够**：每条描述**可判真假**、验收标准**可量化**、横切项全部过了一遍。
**不够**：
- 一条里塞了「且/或/当…时」→ 必须拆。
- 「支持导出」→ 导出什么格式？含哪些列？权限范围？超过多少行怎么办？拆成多条。
- 横切项清单有未打勾且未写「本项目不需要，因为…」的。

> **R-ID 编号纪律**：唯一、不复用、删除的条目留空号不回收（引用可能散落在代码注释里）。

### P6 非目标
**够**：逐条写明**不做什么 + 为什么不做**。
**不够**：空着，或只写一句「其他功能不做」。
> 这是全文最容易被跳过、代价最大的一节。范围膨胀几乎总是从「这个顺手也做了吧」开始。

### P7 约束
**够**：每条标了**硬约束**还是**倾向**。
**不够**：混在一起——实现者无法判断哪条可以在权衡时让步。

### P8 成功定义
**够**：全是数字或可执行的判定。
**不够**：出现「好用」「稳定」「满意」。

## A 层

### A1 系统边界
**够**：写了「**不负责**什么」，且每个外部依赖都注明**失效时的行为**。

### A2 结构与模块职责
**够**：目录树 + 每格职责 + 关联 R-ID，实现者知道新代码该放哪。
**不够**：只有目录树没有职责说明；或出现 `utils/`、`common/`、`helpers/` 这类万能桶
（说明职责没想清楚）。

### A3 关键链路
**够**：能看出数据在每一跳如何变形、在哪落库、**权限在哪一跳裁定**、错误如何冒泡。

### A4 设计原则

**必含一条「不过度设计」**：每条设计只解决对应 R-ID 明写的需求。三条红线——约束别扩面、抽象别提前、字段别镀金。
判据：每条契约能反查到「哪条 R-ID 要的」，反查不到就是未经需求授权的复杂度。
**过度设计比欠设计更危险**：它伪装成「更完备」，却常制造新矛盾（改一个引入一个）。
**够**：是**可以据以驳回一个 PR** 的具体规矩。
**不够**：「代码要整洁」「遵循最佳实践」——这类放 `CLAUDE.md`，且要具体化。

### A5 决策记录 ← 最容易糊弄的一节
**够**：四件套齐全，且「理由」**能被反驳**。
**不够**：
> 反例：「**理由**：更现代、社区活跃、性能更好。」——这三句对任何选型都成立，等于没写。
> 正例：「**理由**：本项目 90% 是表单与列表，团队三人全部熟悉 Vue，
> 且既有管理端已是 Vue 3，共用组件库可省约两周。性能不是本项目瓶颈（P8 的阈值很宽）。
> **已否决**：React——团队无人熟悉，学习成本吃掉工期优势；
> Svelte——生态里缺少符合等保要求的表格组件，需自研。」

**什么必须成为 D-ID**：技术选型 · 数据模型关键取舍 · 每条来源分歧的裁定 ·
与存量冲突的处置 · 任何「三个月后有人会问为什么这么做」的地方。

**推翻旧决策时**：新增一条 D-ID 说明为什么推翻，旧条目标 `已被 D0xx 取代`，**不要删**。

## C 层 —— 精度门槛在这里

**统一标准**：每个契约条目**要么是表格、要么是代码块/schema**。散文不算契约。

### C1 数据模型
**够**：字段的名称·类型·可空·默认值·含义齐全，有索引与关联，写了历史数据兼容策略。
**不够**：只列字段名。可空性和默认值缺失会直接导致实现者猜。

### C2 状态机
**够**：`状态 × 事件` **全表**，含 `✗` 非法格，且写了非法迁移的处理方式。
**不够**：只画箭头图 —— 图里看不出「没画的那条线」是禁止还是遗漏。

### C3 不变量
**够**：每条能对应到 `T1` 的一个检查。写不出检查方式的不变量说明它太模糊。

### C4 接口契约
**够**：路径/入参(含校验)/出参结构/错误情形/鉴权/幂等 + **真实示例**。
**不够**：没有示例；或错误情形只写「返回错误」。

### C7 配置
**够**：每项有单一来源、默认值、敏感标记。
**不够**：出现「其他配置见代码」。

### C8 权限
**够**：写清**服务端在哪一行做裁定**、空范围行为、越权行为、敏感字段处置。
**不够**：只写角色能做什么，没写在哪强制。**前端隐藏不是权限**。

### C9 观测
**够**：明确**哪些字段必须脱敏**。

### C10 / C11
不适用就写 `N/A（<理由>）`。**理由要具体**——「本项目无 UI，交付形态为 CLI」，
而不是光一个 `N/A`。

## T 层

### T1 验收清单
**够**：每个 R-ID 一行，验收方式**具体到能执行**（测试名/命令/操作步骤）。
**不够**：「手工测试」「检查功能是否正常」。
> 没有验收方式的需求 = 不算需求。回 `P5` 补或删。

**拒绝类验收必须写明「以什么理由拒绝」。** 凡是「应当拒绝 / 应当失败 / 应当报错」的验收，
只写"会被拒绝"是不够的——那样实现**用错的理由拒绝了对的东西**也算通过，测试绿了但语义是错的。

| | 写法 |
|---|---|
| ❌ 不够 | 越权访问会被拒绝 |
| ✅ 够 | 越权访问返回**空列表**（不是 403）——`C8` 规定不得暴露资源存在性；断言响应体 `list=[]` 且 `total=0` |
| ❌ 不够 | 非法状态迁移会失败 |
| ✅ 够 | `draft --approve-->` 返回错误码 **`E_INVALID_TRANSITION`**（`C6`），不是通用 500，也不静默忽略 |

判据一句话：**读完这条验收，实现者应该知道"拒绝"要长什么样，而不只是知道"别让它过"。**

### T5 降级策略
**够**：明写「可牺牲的维度」与「不可牺牲的维度」，以及触发降级的信号。
**不够**：不写——那么资源不足时砍需求会变成临场妥协，而临场妥协几乎总是砍掉深度
（每个模块都做一半，结果没有一条链是通的）。
> 判据一句话：**宁可少做几个模块，也不要每个模块都做一半。**

### T2 指标
**够**：每项有数字 + 测量方式。

### T3 停工线
**够**：是**客观可判定的信号**，出现即停。
**不够**：「出现严重问题时停止」——什么算严重？
> 通用起点：权限绕过 · 真实个人信息外泄 · 不可逆数据丢失 · 不变量被破坏 ·
> 为通过而改宽测试。再加项目特有的。

### T4 交付前置
**够**：全是可勾选的客观项。

### T5 施工范围
**够**：每个里程碑有 R-ID 清单、出口条件、**明确不含什么**。
**不够**：只有里程碑名和大致时间。「明确不含」防止里程碑无声膨胀。

## 最后一道尺子

写完通读一遍，每读到一句就问：
**「如果读者不知道我知道的事，这句话还成立吗？」**

不成立的地方，就是冷读门会 FAIL 的地方。与其让它 FAIL，不如现在补。
